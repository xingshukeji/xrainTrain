# 安装与持续维护

这页供应用维护者查阅。基础学员读完 [B6](/basics/version)，知道“导入包”和“租户安装”是两步即可。

维护时要回答一个具体问题：**这个版本是否已经装到正确租户，而且目标用户能正常使用？**

## 从构建到可用，分别检查什么

| 步骤 | 检查结果 |
|---|---|
| 构建 | 生成了指定版本的 .appkg，文件摘要一致 |
| 导入 | 平台包目录中有这个版本 |
| 安装 | 目标租户的 installation 指向这个版本 |
| 操作完成 | 原 operationId 的状态是 Succeeded |
| 功能生效 | describe 是预期字段，记录可正常读写 |
| 用户可用 | 实际使用者有权限，能够完成约定操作 |

例如，包目录中已有 1.0.1，但租户仍装着 1.0.0，页面继续显示旧字段名称就是合理结果。应检查安装，不必再次构建同一版本。

## 升级前做四件事

1. 确认包版本、内容和摘要。内容变更使用新版本，不覆盖旧版本。
2. 读取目标租户的 installation 和 revision。
3. 查看 preview 列出的变化、绑定、冲突及确认项，处理缺少的信息。
4. 保存本次 requestId，再提交安装并查询进度。

revision 是修订号，用来检查提交前安装状态有没有被别人修改。

B6 的升级只改显示名称，原记录应保留。修改字段类型、删除字段或增加必填项时，要另行检查对已有数据的影响。

完整命令见[构建、导入与安装](/reference/tools#构建导入与安装)。

## 超时后先查原操作

网络超时不表示服务器停止执行。使用原 requestId 查询：

```http
GET /api/application/v1/operations/{requestId}
```

| 查到的状态 | 下一步 |
|---|---|
| 仍在运行 | 继续查询同一操作 |
| 成功 | 核对 installation、字段和原记录 |
| 明确失败 | 按错误处理绑定或冲突，再决定后续操作 |
| 操作结果与当前安装不一致 | 保留信息，请环境维护者核对 |

不要通过换 requestId 或卸载应用来“试着恢复”。恢复组件、重新导入、卸载和回滚的影响不同，应按实际问题选择。

## 分清哪些东西随包更新

`.appkg` 提供平台资源配置，不包含所有 Node.js 服务或 React 页面代码。

| 改动 | 检查哪个版本 |
|---|---|
| 对象、字段等包资源 | 应用包和租户安装版本 |
| 自建页面、业务服务 | 对应应用程序版本 |
| 模型连接、运行参数 | 环境配置 |
| 用户职责和数据访问 | 租户成员、角色与权限 |

一个维护者可以通过角色承担多个应用的工作，无须为每个应用新建管理员账号。人员职责变化时，检查应保留或撤销的权限。

## 留下足够的维护记录

记录目标租户、操作人、原版本、目标版本、operationId、最终状态，以及一次实际读写结果。分享记录前移除密码、令牌和业务数据。

若结果还不确定，就写明正在查询的操作编号，方便继续处理，不重复执行来覆盖上一次结果。
