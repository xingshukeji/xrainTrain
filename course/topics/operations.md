# 安装与持续维护

这一页面向承担应用维护职责的人。基础学习者先完成[B6 标签升级](/basics/version)，认识版本和有效定义即可。

第一次阅读只练一个判断：看到“构建成功”时，还缺哪些信息才能确认某位学员可用？用下表逐项回答即可。只有实际承担维护任务时，再执行后面的升级或恢复步骤；本文不要求为练习卸载已有应用。

## 用不同证据回答不同问题

| 你的问题 | 检查什么 |
|---|---|
| 源码能生成包吗？ | 服务端构建结果、包身份、版本及文件摘要 |
| 平台知道这个版本吗？ | 导入后的包版本目录 |
| 当前租户安装了它吗？ | installation 的租户、版本、revision |
| 本次操作成功了吗？ | 原 operationId 的终态与错误 |
| 组件真的生效了吗？ | 有效 describe、资源目录及目标操作 |
| 当前人员能使用吗？ | 该人员的准入、对象/字段权限、数据范围及真实动作 |

不能用“目录出现名称”替代安装结果，也不能用“管理员安装成功”替代普通成员的使用结果。

## 升级前先固定这四项

1. 固定要交付的包版本及完整性信息。内容变化必须形成新版本，不覆盖同一不可变身份。
2. 读取目标当前 installation 和 revision，确认是预期租户与包。
3. 预检变更、绑定、冲突和必要确认，逐项判断影响。预检未就绪时不提交。
4. 记录本次逻辑操作的 requestId，再提交一次；根据 operation 查询后续状态。

本课 1.0.0 → 1.0.1 只修改“内容”标签。对象 ID、字段 ID、API 名和原记录 ID 保持不变。改字段类型、删除字段或改变必填约束可能影响存量数据，不能照搬这个无损小例子的结论。

## 超时后先查原操作

如果提交后网络断开，服务器可能仍在执行。用原 requestId 查询 GET `/api/application/v1/operations/{requestId}`，再核对实际 installation。不要为了“试一下”换一个 requestId 重复安装。

| 观察结果 | 下一步 |
|---|---|
| 仍在执行 | 继续读取原操作，保留目标与编号 |
| 成功 | 比对实际安装版本及有效组件 |
| 明确失败 | 按返回的具体冲突或绑定问题处理，再决定是否需要新操作 |
| 原操作与当前状态不一致 | 停止扩大变更，交给环境所有者核对 |

恢复已有安装组件、重新导入包、卸载应用和回滚版本是不同操作。按目标的既有维护合同选择。卸载可能改变组件与数据可用性，不能当作通用重试手段。

## 人员和环境也需要持续维护

固定身份按实际人员和用途复用。人员加入租户、进入应用、获得业务角色是不同关系；职责变化时核对需要保留和撤销的范围，不按每个租户或任务重复创建管理员。

平台资源包、Host/Client 程序、在线智能体定义和环境配置各自交付。`.appkg` 不包含所有 Node/React 页面代码。实际变更涉及哪一层，就核对哪一层的版本和结果。

环境启动、服务恢复和既有流水线执行使用项目维护入口。课程不重新实现部署工具，不把测试环境的账号、地址或凭据写进公开教程。

## 一次维护的最小记录

保留目标、操作者职责、原版本、目标版本、原 operationId、终态和最小业务回读结果。结果未知时明确写未知，不用重新执行覆盖第一次的事实。发送给其他人前移除凭据、用户数据与不必要的运行细节。
