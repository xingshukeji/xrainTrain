# B7 · 看懂错误并继续

接口报错时，先回答两个问题：**我发了什么？平台返回了什么？** 从一个最小错误开始，通常比反复重试更容易找到原因。

## 例子一：字段名多写了一个 s

你想保存便签，却提交了：

```json
{ "values": { "contents__c": "你好，XRain" } }
```

在 describe 中查到的字段名是 `content__c`，请求里却是 `contents__c`。把字段名改正确，再提交即可；不需要创建新字段。

| 检查位置 | 结果 |
|---|---|
| describe.fields | `content__c` |
| 你的请求 | `contents__c` |
| 应修改的位置 | 请求中的字段名 |

## 例子二：忘了填写必填内容

下面的创建请求没有填写任何字段：

```json
{ "values": {} }
```

教学环境返回 `400 / platform.data.validation_failed`。查看 describe，发现 `content__c` 的 `required=true`，也就是必填。

修正后的正文是：

```json
{ "values": { "content__c": "你好，XRain" } }
```

这次问题是输入缺少内容，不是密码错误。先读错误，再决定检查哪一项。

## 常见状态码，先记住这些

| 返回 | 通常先检查什么 |
|---|---|
| 401 | 登录是否过期，接口是否接受当前登录方式 |
| 403 | 当前用户是否有对象、字段和这条记录的访问权限 |
| 400 | 字段名、类型、必填项和长度 |
| 404 | 地址、对象 API 名、recordId、租户及记录是否已删除 |
| 409 | 旧值或版本条件是否与当前数据一致 |
| 5xx | 保存错误码、时间和 traceId，交给服务维护者 |

状态码只是线索。比如 404 还可能与记录不可见有关；具体原因要结合错误消息和接口说明。更多情况查[按现象排错](/help/errors)。

## 超时后，为什么不能直接再点一次

假设你创建便签时网络断开：平台可能已经保存，只是响应没有到达。直接再创建，可能得到两条相同记录。

先刷新列表，按自己的创建时间和内容查找；安装操作则用原 `requestId` 查询进度。确认上次没有成功后，再处理重试。

## 请 AI 帮忙，提供一个具体问题

```text
我在修改自己的学习便签，字段是 content__c。
我先读到“你好，XRain”，想改成“明天交报告”。
PUT 请求的 expectedValues.content__c 是“你好，XRain”。
现在返回 409，错误码是 platform.data.concurrency_conflict。
请解释原因，并告诉我下一步应该读取什么。
```

好的回答应先让你重新读取当前内容，再比较差异。若建议直接去掉 `expectedValues`，要考虑是否会覆盖别人的修改。

分享请求时删去密码、Token 和真实业务数据，保留必要的字段名、错误码与示例值即可。

## 自己做一次

从本页两个错误中选一个，用四句话说明：

1. 我想做什么。
2. 我实际发了什么。
3. 哪一项与字段说明不一致。
4. 改完后怎样确认结果。

::: details 示例答案
我想创建便签。请求的 values 为空，但 content__c 是必填字段。补上 content__c 的文字后重新提交，再按返回的 recordId 打开记录，确认内容正确。
:::
