# B5 · 用户、角色与权限

**登录成功，只说明平台知道你是谁；能否查看或修改数据，还要看权限。**

例如，一个账号能安装教学包，创建便签时却收到 403。返回提示缺少 `platform.entity.xrainlearn__note__c.create`，意思是没有“创建便签”的权限。给这个账号配置对应权限后，才能创建。

## 四个名称，用一个例子串起来

假设要让一组学员查看、新建和修改便签，可以这样组织：

**用户 → 学员角色 → 便签练习权限集 → 查看、新建、修改权限**

| 名称 | 可以怎样理解 | 例子 |
|---|---|---|
| 用户 | 使用平台的人 | 一个学员的账号 |
| 权限 | 允许做的一项操作 | 查看便签、创建便签 |
| 权限集 | 放在一起管理的一组权限 | 便签练习需要的读写权限 |
| 角色 | 按工作职责给用户分配权限集 | 学员角色关联便签练习权限集 |

一个用户可以有多个角色。简单场景也可以直接给用户分配权限集，不必每次都新建角色。

[操作视频](/platform-tour)从 1:08 开始演示创建自定义权限、权限集、角色，再关联已有成员。具体按钮见[视频下方的文字步骤](/platform-tour#自定义权限)。

### 自定义权限和对象权限有什么区别

便签的“查看、创建、编辑”等权限由平台提供。要允许某人创建便签，应从权限目录选择便签对象的 `create` 权限。

自定义权限用于你自己实现的业务动作，例如“批准报销”。业务代码需要检查这项权限，才会决定是否允许批准。**只创建一个叫“批准报销”的权限，并不会自动实现报销审批。**

视频中的 `custom.xraintrain.video.read` 用于演示配置关系，没有接入业务代码，因此不会改变便签的读写权限。

## 收到 403，先查哪三件事 {#收到-403先查哪三件事}

| 检查 | 具体例子 |
|---|---|
| 用户和租户是否正确 | 是否登录了约定的账号、进入了练习租户 |
| 是否有这项操作的权限 | 能查看便签，不一定能创建或编辑 |
| 是否能操作这条记录和这个字段 | 能读自己的便签，不一定能读其他人的便签 |

用 B1 的终端查看当前登录信息：

```powershell
$context = Invoke-RestMethod -Uri "$base/api/service/authen/v1/account/context" -Headers $headers
$context | Select-Object tenantId, userId, scope
```

`tenantId` 是当前租户，`userId` 是当前用户，`scope` 表示登录范围。将它们与环境维护者提供的信息对照。

再看错误中的具体权限名。比如末尾是 `create`，就先检查创建权限；不要因为能读取，就认为也能创建。

::: details 按需查：应用入口、字段和记录范围
![检查登录、租户、应用访问、对象字段权限和记录范围](/diagrams/access.svg)

进入某个应用可能还需要该应用的访问权限；直接调用平台接口时，按那个接口的要求检查。

`describe.object.access` 列出当前用户可读、可创建和可修改的字段。页面隐藏字段不能代替服务端权限检查。

记录的 Owner、共享规则和人工分享会影响可访问的数据范围。Owner 是记录归属，业务负责人是工作分工，创建人表示谁创建了记录，三者可以不同。分享记录时，接收人仍需对象和字段权限。
:::

## 撤销一个角色，为什么还可能有权限

权限可能来自多个地方。假设同一个人既通过角色获得“查看便签”，又直接关联了包含该权限的权限集。移除角色后，直接关联仍然有效。

因此，检查“权限是否已撤销”时，要查看这个用户的其他角色和直接权限集。操作步骤和数据分享见[数据专题](/topics/data#记录归属与分享)。

## 自己做一次

1. 查看自己的 `context`，确认用户和租户。
2. 在 `describe.object.access` 中，找出自己可创建、可编辑的字段。
3. 判断：用户 A 有便签读取权限，用户 B 没有；两人请求同一条便签，A 返回 200，B 返回 403。问题出在便签没有保存，还是 B 的权限？

::: details 对照答案
A 能读到同一条记录，说明记录已经存在。应先检查 B 缺少的对象、字段或记录访问权限。

要在平台复现，需要维护者准备两名已有测试用户，由各自正常登录。没有权限维护职责的学员，把错误码和缺少的权限名交给维护者即可。
:::
