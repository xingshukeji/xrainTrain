# B5 · 用户、角色与权限

李四想修改张三的一条便签。登录成功后，还要回答三件事：**李四有没有编辑权限、内容字段能不能改、张三的这条便签是否在允许范围内。**

读完本课，应能分清：

- **权限规定可以做什么；角色和权限集负责把权限分配给人。**
- **同一权限可能有多个来源；一次操作需要同时满足它涉及的条件。**
- **能进入应用、能管理应用、能修改业务数据，分别判断。**

## 1. 权限分类：它控制什么操作 {#权限分类}

[![权限按控制对象分为管理权限、数据权限、接口与功能权限；数据权限包括对象与字段，自定义业务权限需要业务代码检查](/diagrams/permission-types.svg)](/diagrams/permission-types.svg)

[打开分类 SVG 大图](/diagrams/permission-types.svg)

例如，“允许编辑便签”是对象权限；“允许修改便签内容”是字段权限。对象允许编辑后，某个字段仍可以只读。记录范围再决定李四能改自己的便签，还是也能改张三分享给他的便签。

便签的对象、字段标准权限由平台生成。要允许创建便签，从目录选择对象的 `create` 及所需字段权限。**不需要另建一个同名的自定义权限。**

自定义权限适合“批准报销”这类自己实现的业务动作。业务代码检查它后，才能控制审批。视频中的 `custom.xraintrain.video.read` 只演示配置关系，没有接入业务代码，因此不会改变便签的读写权限。

::: details 按需查：权限名称怎样对应分类

| 名称形式 | 控制什么 |
|---|---|
| `platform.entity.对象名.动作` | 对象的查看、新建、编辑、删除、导出 |
| `platform.field.…` | 字段的查看、新建时写入、编辑 |
| 其他 `platform.*` | 平台拥有的管理能力或业务动作，按目录中的说明选择 |
| `api.*`、`tenantApi.*` | 指定 API 的调用许可；通过后仍要检查业务数据权限 |
| `listview.*` | 指定列表视图的使用权限 |
| `httpInterface.*.execute` | 指定 HTTP 接口的执行权限 |
| `custom.*` | 业务自己定义并检查的权限 |

前缀表示权限的归属与用途，不能单凭前缀判断用户是否已经获得权限。权限目录中的真实名称是配置依据。

字段没有单独的 `export` 权限。对象 `export` 是导出的附加要求；它不补齐对象读取、字段读取或记录范围。
:::

## 2. 权限怎样分配给用户 {#权限如何分配}

要让一组学员查看、新建和修改便签，维护者可以把这些权限放进“便签练习权限集”，关联到“学员角色”，再把学员加入角色。

**权限 → 权限集 → 角色 → 用户**，这是按职责分配的一条常用路径。

[![具体权限加入权限集后，可通过角色或直接分配给用户；全体员工来源也参与同一用户的有效权限计算](/diagrams/permission-grants.svg)](/diagrams/permission-grants.svg)

[打开授权来源 SVG 大图](/diagrams/permission-grants.svg)

权限集方便复用一组能力，角色方便按职责分配。简单场景可以直接给用户分配权限集，不必每次都新建角色。一个用户也可以关联多个角色。

当前租户的有效成员还会自动适用“全体员工”固定权限集；已确认启用的全员包权限集也可能提供权限。这些来源与角色、直接分配一起计算，并继续遵守启停、拒绝和有效期等规则，不能只数关联了多少项。

### 撤销一个角色，为什么还可能有权限

李四通过“学员角色”获得查看便签的权限，同时又直接关联了“便签练习权限集”。移除角色，只撤掉这条角色来源，直接分配仍然有效。

因此，**撤权要核对这个用户的全部有效来源，再用原账号验证结果。** 只看某个角色的权限页，不能得出这个用户的最终权限。

### 应用管理员与业务角色有什么区别

应用管理员负责维护该应用获准范围内的角色、权限集和分配。新增授权受到应用可授予范围的限制；管理权限本身不代表本人拥有所有业务读写权限。

应用内角色仍使用上图的授权关系。应用是否向李四开放，则由应用准入判断。发布范围、管理职责、业务权限可以不同。

## 3. 一次修改请求怎样判断 {#请求如何判断}

下面以普通业务账号修改便签为例。蓝灰色箭头表示满足条件后继续；红色箭头表示停止本次修改。**任一相关条件不满足，都不能用其他层的权限代替。**

[![修改便签依次核对身份与租户、接口调用、对象编辑、字段编辑、记录范围和业务规则，每一步不满足都停止本次修改](/diagrams/permission-request.svg)](/diagrams/permission-request.svg)

[打开请求判断 SVG 大图](/diagrams/permission-request.svg)

图中表示判断依赖，具体接口可能合并或提前检查，不是内部调用时序图。进入独立应用的新会话前，还会检查应用是否启用、用户是否在发布范围内；准入通过不会自动增加数据权限。

常用记录读写 API 的入口许可已由全体员工基础权限提供，**不等于所有成员都能读写所有对象**。对象、字段和记录范围继续决定实际数据访问。

读取记录与修改记录也有区别：读取时，不可读字段可能被过滤，列表也只返回允许范围内的记录；不能把“少了一列”或“列表为空”直接判断成保存失败。

## 4. 用同一条便签看四种结果 {#便签权限对照}

假设李四的身份、租户、接口许可和数据格式都正确。每行只改变表中所说的条件：

| 李四当前的情况 | 结果与原因 |
|---|---|
| 只有查看权限，没有便签对象的编辑权限 | 不能修改。查看与编辑是不同操作 |
| 对象可编辑，但“内容”字段不能编辑 | 不能提交该字段的修改。对象权限不替代字段权限 |
| 对象和字段都可编辑，但张三的便签未向李四开放 | 不能修改这条记录。还需要满足记录范围 |
| 对象和字段都可编辑，记录范围允许李四编辑，业务规则也通过 | 可以修改 |

Owner 表示记录归属，可能与业务负责人、创建人不同。记录团队、共享规则和人工分享可以影响访问范围。分享一条记录时，接收人仍需对象和字段权限；只读分享也不会变成编辑授权。详细操作见[记录归属与分享](/topics/data#记录归属与分享)。

## 收到 403，先查哪三件事 {#收到-403先查哪三件事}

1. **确认实际调用者和租户。** 页面操作看登录用户；定时任务或机器人代发还要看实际执行账号。
2. **确认本次动作需要的权限及其来源。** 有查看权限不代表有创建或编辑权限；配置了权限集也不代表已经分配给此人。
3. **确认具体字段和记录范围。** 使用原账号、原请求和原记录检查，不用管理员成功代替。

用 B1 的终端查看当前登录信息：

```powershell
$context = Invoke-RestMethod -Uri "$base/api/service/authen/v1/account/context" -Headers $headers
$context | Select-Object tenantId, userId, scope
```

`tenantId` 是当前租户，`userId` 是当前用户，`scope` 表示登录范围。再用 `describe.object.access` 查看允许的操作及可读、可创建、可编辑字段。

错误给出了具体权限名时，先查该项。例如 `platform.entity.xrainlearn__note__c.create` 表示便签对象的创建权限。字段拒绝不一定公开具体字段或权限名，需要由维护者结合原请求定位。没有权限维护职责的学员，提供请求、错误码和操作目标即可。

1. 查看自己的 `context`，确认用户和租户。
2. 在 `describe.object.access` 中找到可创建、可编辑字段。
3. 回看便签对照表，判断：给第三行的李四再加一次同样的对象编辑权限，能否解决问题？

::: details 对照答案
不能。第三行已具备对象和字段编辑权限，缺的是这条记录的编辑范围。维护者应按原业务职责检查记录归属或分享，重复授予同一对象权限不会扩大记录范围。

要实际验证允许和拒绝，由维护者准备已有测试用户，各自正常登录并操作同一条合成记录。上表是规则推演，不表示浏览器里的答题已经完成平台授权验证。
