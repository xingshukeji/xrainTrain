# B4 · 每次认识一种字段

“内容”是文本。现在只扩展你对**字段类型与保存值**的认识，不把一整套业务一次塞进便签。

## 标签变化，为什么不一定要改代码

人看到“内容”，接口使用 `content__c`。标签是展示名称，API 名是程序引用。另一个对象也可能有“内容”标签，但两者属于不同对象。

`describe` 中的 `type` 表达业务类型，`presentation` 表达如何编辑和显示。把一个字段显示为多行，并不自动改变保存类型或访问权限。页面应根据当前有效定义选择控件，并根据 `object.access` 决定可读、可建和可改字段。

## 常见类型先知道怎样存

| 类型 | 典型信息 | HTTP 保存值要点 |
|---|---|---|
| `Text`、`LongText` | 标题、说明 | 字符串；Text 按声明长度限制 |
| `Boolean` | 是否启用 | `true` / `false`，不是字符串 `"true"` |
| `Number` | 件数 | 按元数据约束使用数值 |
| `Decimal`、`Money` | 精确数量、金额 | Runtime JSON 使用十进制字符串，如 `"10.20"`，保留精度 |
| `Date` | 业务日期 | 日期值，不凭空添加时区换算 |
| `DateTime` | 发生时刻 | 按 `temporalContracts` 和当前地区上下文处理明确时刻 |
| `Picklist`、`MultiPicklist` | 类别、多个标签 | 从 options 取得稳定保存值；多选按数组合同 |
| `Lookup` | 关联某个对象的一条记录 | 保存目标记录 ID，候选来自目标对象 |
| `UserRef` | 负责人 | 保存有效人员引用，使用人员候选合同 |

包源码的值格式与 Runtime HTTP 值格式各有合同。尤其是精确数字，不能把 HTTP 示例直接复制成包内种子记录，也不能先转成 JavaScript 浮点数再声称保留了精度。

日期与时刻也不同：2026-10-25 是一天，某时区当天 09:00 是需要解释的当地时间。涉及跨地区或定时任务时，继续读[时间与自动化](/topics/automation#时间与执行人)。

## 一个选项例子：工作或生活

这是**独立的概念练习**，不要求修改前几节已经验证的便签包。假设另一个教学对象有 `category__c`，选项接口返回如下含义：

| label | value |
|---|---|
| 工作 | `work` |
| 生活 | `life` |

选择“工作”时，应用保存 `work`。元数据里的选项记录 ID 用于定义与管理；运行时到底接受哪种值，以该字段 options 的实际响应为准。不要仅凭标签猜值。

查询选项的接口族是：

```http
GET /api/data/v1/entities/{entityCode}/fields/{fieldApiName}/options
```

只有真实选项字段才使用这个入口。`content__c` 是 Text，对它请求 options 是类型使用错误，不会自动变出一个选项集。实际添加选项字段时，先准备独立样例和对应版本，再做“保存 → 回读 → 显示标签”的小练习。

## 一个关联例子：便签归入一个分类

另一个独立例子是“分类”对象和指向它的 Lookup 字段：分类记录的名字供人识别，关联保存其记录 ID。即使分类名称以后修改，关联仍指向同一个 ID。

关系需要两个对象，所以它不属于首课的一对象起点。要动手时，只准备一个分类、一个 Lookup 和两条合成记录；不要顺便加入组织、客户、任务和审批。

`UserRef` 还有固定人员对象与人员资格规则，不把任意 Lookup 的 options 接口套过去。能看到某人的名字，也不等于能以该人的身份执行操作。
